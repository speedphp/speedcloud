# speed 1.3.2：`@Service` 装饰器（声明即注册）

> 本章教程配套 speed 1.3.2（9 模块之①注册中心的第三个 patch）。阅读前提：speed 1.3.1（本地注册表，见 `docs/1.3.1-本地注册表.md`）。
>
> 配套代码：`src/registry/service-registrar.ts`、`src/core/service.decorator.ts`；可运行验证：`npm test`（`test/service.test.ts`）。

---

## 一、为什么：注册时机是「声明即注册」的真正难点

1.3.1 交付了本地注册表，能手动 `register` 一个实例。但「手动注册」不是目标——Spring Cloud 的体验是**给类加个注解，服务就被发现了**。speed 要的是 `@Service`：**声明即注册**。

这件事听着简单，做起来有一个绕不开的坎：**注册时机**。

注册中心要记录的是「哪个服务现在跑在哪个地址」，而地址（host:port）是一个**运行时事实**，只有服务真的监听成功之后才确定：

1. 标准类装饰器（TC39）的 `addInitializer(fn)` 回调里，`this` 是**类本身（构造函数）**，不是实例。所以装饰器只能拿到类名，拿不到实例，更拿不到实例里的 `ServerFactory`。
2. 真实端口要等 `server.start(port)` 之后才有（端口还可能被系统动态分配，由 `server.address().port` 返回）。而 `start` 是在 `main()` 里、实例创建之后才发生的事。

如果把「注册」写在装饰器里，那**注册那一刻端口还没确定**，只能谎报一个假端口——这正是 Eureka / Nacos 最忌讳的事：**实例信息必须准确**。注册表里的每一条记录都是「真实可连」的地址，任何一条假地址都会让调用方连到空气上。

所以 speed 把「注册」拆成两个阶段：

| 阶段 | 动作 | 时机 | 能拿到什么 |
|---|---|---|---|
| **声明** | `@Service` 装饰器 | 类定义时 | 类名、服务名、group、version（静态身份） |
| **提交** | `serviceRegistrar.register()` | 启动后 | 真实 host、真实 port（运行时网络事实） |

**装饰器只声明「我是谁」，不声明「我在哪」**；「我在哪」必须等启动完成后、由真实监听地址来回答。

顺带厘清两个易混概念：

- **同名多实例** = 一次声明 + N 次提交。同一个服务名，多个进程、多个端口各注册一次，这是负载均衡的基础，**合法**。
- **同名异类** = 同一个服务名被多个不同的类声明。这通常是配置失误（两个类都叫 `user-service`），声明时 `console.warn` 提醒，但**不阻断**（万一是刻意的多实现场景，交给提交阶段区分）。

## 二、怎么用：四种写法 + 一次提交

### 2.1 引入

`@Service` 从 `speed/core`（或主入口 `speed`）引入，提交用 `serviceRegistrar`：

```ts
import { Service, serviceRegistrar } from "speed";
```

### 2.2 四种 `@Service` 写法

```ts
@Service                                  // ① 无参：服务名默认用类名
class PaymentService {}

@Service()                                // ② 显式空参：同上
class OrderService {}

@Service("user-service")                  // ③ 字符串：指定服务名
class UserService {}

@Service({ name: "inventory-service", group: "default", version: "v2" })  // ④ 对象：带元数据
class InventoryService {}
```

### 2.3 启动后提交一次

`@Service` 只是**声明**。服务 `start` 之后，用真实监听地址提交一次：

```ts
// 完整可运行片段（配合 typespeed 的 @app）
@app
@Service("user-service")
class Main {
    @autoware(ServerFactory)
    public server!: ServerFactory;

    public main() {
        const port = 8080;
        this.server.start(port);
        // 声明/提交分离：这里才拿得到真实 port
        serviceRegistrar.register("user-service", { host: "127.0.0.1", port });
    }
}
```

提交后，就能查到该服务的实例：

```ts
serviceRegistrar.getRegistry().getInstances("user-service");
// => [ { host: "127.0.0.1", port: 8080, registeredAt: ..., metadata: { ... } } ]
```

### 2.4 同名多实例 vs 同 host:port 去重

```ts
serviceRegistrar.register("user-service", { host: "127.0.0.1", port: 8080 });
serviceRegistrar.register("user-service", { host: "127.0.0.1", port: 8081 });  // 多实例，合法
serviceRegistrar.register("user-service", { host: "127.0.0.1", port: 8080 });  // 重复：只更新，不新增
```

> 和 1.3.1 一致：**同名多实例是正常的**（`host:port` 不同），**同 `host:port` 才是重复**。

### 2.5 `Registration` 句柄

`register` 返回一个注册句柄，承载后续「续期 / 注销」能力：

```ts
const reg = serviceRegistrar.register("user-service", { host: "127.0.0.1", port: 8080 });

reg.instanceId;  // "127.0.0.1:8080" —— 实例稳定标识
reg.renew();     // 续期（1.3.2 先刷新 registeredAt 占位，1.3.3 改为心跳）
reg.deregister(); // 注销，返回是否真的移除成功
```

## 三、原理：两套数据解耦——声明表与实例表

1.3.2 的核心是**把「声明」和「实例」拆成两套互不耦合的数据**：

| 数据 | 载体 | 键 | 内容 |
|---|---|---|---|
| 声明表 | `ServiceRegistrar.declarations` | 服务名 → 声明列表 | 类名、服务名、group、version（静态身份） |
| 实例表 | `LocalRegistry.instances`（1.3.1 的两级 Map） | 服务名 → 实例列表 | host、port、registeredAt、metadata（运行时事实） |

### 3.1 声明：装饰器只调 `declare`

`@Service` 展开后，最终只做一件事——在 `addInitializer` 里调用 `declare`：

```ts
export function Service(...args: any[]): any {
    // 直接装饰：@Service
    if (args.length === 2 && args[1].kind === "class") {
        const context = args[1];
        context.addInitializer(function (this: any) {
            serviceRegistrar.declare(this.name, {});   // this.name 即类名
        });
        return;
    }
    // 工厂形式：@Service("name") / @Service({...})
    const options = resolveOptions(args[0]);
    return function (value: any, context: StdClassContext): void {
        context.addInitializer(function (this: any) {
            serviceRegistrar.declare(this.name, options);
        });
    };
}
```

`declare` 只登记身份，**不碰注册表**。它做三件事：

- **幂等**：同一类重复声明（重复 import / 多次装饰）不重复登记；
- **同名异类告警**：已有别的类占用该服务名时 `console.warn`，不阻断；
- **入表**：把声明 push 进「服务名 → 声明列表」。

### 3.2 提交：`register` 合并元数据后下沉

`serviceRegistrar.register(serviceName, instance)` 是唯一写实例的入口：

```ts
register(serviceName: string, instance: ServiceInstance): Registration {
    const declarations = this.declarations.get(serviceName);
    if (!declarations || declarations.length === 0) {
        throw new Error(`[speed] 服务名 "${serviceName}" 未通过 @Service 声明，无法注册。`);
    }
    const decl = declarations[0];
    const metadata = { ...(instance.metadata ?? {}) };
    if (decl.group !== undefined) metadata.group = decl.group;
    if (decl.version !== undefined) metadata.version = decl.version;
    return this.registry.register(serviceName, { ...instance, metadata });
}
```

两个关键点：

- **未声明不许注册**：没有 `@Service` 声明的服务名直接抛错，强制走「声明 → 提交」两阶段；
- **声明元数据合并进实例**：`@Service({ group, version })` 里的静态身份，在提交时自动合并进实例 `metadata`（调用方自己传的 metadata 优先，声明只补缺省）。

### 3.3 `Registration` 句柄：为心跳 / 摘除留口

1.3.1 的 `register` 返回 `ServiceInstance`，1.3.2 改为返回 `Registration` 句柄：

```ts
export interface Registration {
    readonly instanceId: string;   // "host:port"，与去重键一致
    renew(): void;                 // 续期
    deregister(): boolean;         // 注销
}
```

句柄通过闭包持有「实例引用 + 服务名」，所以：

- `renew()` 直接刷新 `target.registeredAt`（1.3.2 占位，1.3.3 改为刷 `lastHeartbeat`）；
- `deregister()` 转调 `registry.unregister(serviceName, host, port)`。

这样调用方拿到句柄就拥有了「续期 / 摘除」两个未来能力，接口一次定对。

### 3.4 `Registry` 接口：为 Nacos 抽象

1.3.2 把 1.3.1 的 `LocalRegistry` 抽成 `Registry` 接口：

```ts
export interface Registry {
    register(serviceName: string, instance: ServiceInstance): Registration;
    unregister(serviceName: string, host: string, port: number): boolean;
    getInstances(serviceName: string): ServiceInstance[];
}
```

`ServiceRegistrar` 内部持有一个 `Registry` 引用（默认 `new LocalRegistry()`），业务代码面向接口编程。到 1.3.8 加 Nacos 实现时，只需换一个实现类，上层无感知。

## 四、怎么扩展：从这里走向心跳、发现与 Nacos

1.3.2 把「注册」拆成了声明/提交两阶段，并留下了两个明确的接口位（`Registration` 句柄、`Registry` 接口）。后续 patch 只需在对应位子上填实现：

| patch | 内容 | 落到哪个扩展位 |
|---|---|---|
| 1.3.3 | 心跳 | `Registration.renew()`：从刷新 `registeredAt` 改为刷新 `lastHeartbeat` |
| 1.3.4 | 健康检查 + 摘除 | `Registration.deregister()` + `ServiceInstance.status` |
| 1.3.5 | 服务发现 | 封装 `Registry.getInstances()` 并做健康过滤 |
| 1.3.8 | Nacos 适配 | `Registry` 接口的第二个实现（替换 `LocalRegistry`） |

**给贡献者的扩展点**：

- **host/port 只能出现在提交侧**，不要试图塞回装饰器。装饰器拿不到实例、也拿不到真实端口，塞进去一定是假数据——这是 1.3.2 两阶段设计的根本原因；
- 新增能力优先挂在 `Registration`（续期/摘除）或 `Registry`（注册/注销/查询）上，不要绕过它们直接碰内部 Map；
- `ServiceInstance.metadata` 语义（`group` / `version` / `weight` / `tags`）随 patch 逐步明确，声明侧 `ServiceOptions` 只放静态身份字段（name/group/version），不要放运行时字段。
