# speed 1.3.0：脚手架与项目骨架

> 本章教程配套 speed 1.3.0（9 模块之①注册中心的第一个 patch）。阅读前提：了解 typespeed（单体框架，对标 SpringBoot）与 speed 的定位（微服务编排，对标 SpringCloud）；本文是《TypeScript技术实战》体系的 speed 系列第一篇。
>
> 配套代码：本仓库 `src/scaffold/`（脚手架命令 + 模板）；可运行示例：`speed new demo`。

---

## 一、为什么：先有「门面」，再有微服务

speed 要管的是「一群 typespeed 服务」。但在注册中心、网关、RPC 这些能力落地之前，用户得先能**用一行命令建出一个标准项目**。这就是 1.3.0 的全部目标：

1. **`speed new` 脚手架**——「装完就能跑」的标准项目模板，是 speed 的第一印象；
2. **标准装饰器栈固化**——speed 与 typespeed legacy 模式的根本区别，必须在模板里锁死；
3. **目录约定**——服务类放 `src/`、配置放 `config.json`，为后续模块铺好轨道。

顺带解决了一个卡点：typespeed 2.6.6 的标准装饰器 `@app` 存在启动缺陷（类装饰器 initializer 的 `this` 是类本身，代码却取了 `this.constructor`，拿到 `Function` 后报 `main.main is not a function`）。speed 依赖标准装饰器栈，所以随 1.3.0 一并修复并发布 **typespeed 2.6.7**。

## 二、怎么用：一条命令建项目

### 2.1 安装

```bash
npm install speed -g
```

### 2.2 创建项目

```bash
speed new demo
cd demo
npm install
npm run start
```

启动后访问 `http://127.0.0.1:8080/health`，返回：

```json
{"status":"up"}
```

### 2.3 生成的项目长什么样

```
demo/
├── package.json      # 预置 speed + typespeed 依赖、start/build/test 脚本
├── tsconfig.json     # 标准装饰器三开关（见 3.2）
├── .gitignore
└── src/
    ├── main.ts       # @app 入口骨架（标准装饰器）
    └── config.json   # 应用配置（typespeed 启动时自动读取）
```

`src/main.ts` 核心就三件事：`Symbol.metadata` polyfill → `@app` 标注入口类 → `main()` 里用 `ServerFactory` 起服务。

## 三、原理：脚手架与标准装饰器

### 3.1 脚手架实现

脚手架复用了 typespeed 的思路：**commander 解析命令 + 模板字符串渲染**。

- 命令入口 `src/scaffold/command.ts`：`speed new <projectName>`，创建目录、逐个写文件；
- 模板 `src/scaffold/templates/*.tpl`：占位符 `###appName###` 在生成时替换为项目名；
- `postbuild` 脚本把模板复制进 `dist/scaffold/templates`，发布后 CLI 从包内读取模板；
- `package.json` 的 `bin` 字段把 `speed` 指向 `dist/scaffold/command.js`。

```ts
// command.ts 核心（节选）
program.command('new <projectName>')
    .description('Create a new speed project.')
    .action((projectName) => {
        // ...创建目录
        mkFile("package.json", appPath, projectName);
        mkFile("tsconfig.json", appPath, projectName);
        mkFile("main.ts", appPath + "/src", projectName);
        // ...
    });

function mkFile(fileName, targetPath, projectName) {
    const tpl = fs.readFileSync(`${__dirname}/templates/${fileName}.tpl`, "utf-8");
    fs.writeFileSync(`${targetPath}/${fileName}`, tpl.replace(/###appName###/g, projectName));
}
```

### 3.2 tsconfig 三开关：标准装饰器的「护照」

speed 项目与 typespeed 书里 legacy 模式的根本区别，就在 `tsconfig.json` 三个开关：

```jsonc
{
    "experimentalDecorators": false,   // 关掉 legacy 装饰器
    "emitDecoratorMetadata": false,    // 标准模式必须关（开着会报 TS5052）
    "lib": ["es2022", "esnext.decorators"]  // 标准装饰器类型
}
```

**必须固化进模板**——用户装完就能编译，不允许手动改配置。

### 3.3 `@app` 引导链

标准装饰器下，`@app` 的执行链是：

```
main.ts 加载
  → Symbol.metadata polyfill（Node 22/24/26 都没有，缺了 context.metadata 直接 TypeError）
  → import { app, ... } from "typespeed"
  → @app 装饰器执行：ctx.addInitializer(() => startApp(this))
  → startApp：扫描并加载核心文件 + 应用目录文件
  → new Main() → main() → ServerFactory.start(8080)
```

### 3.4 为什么模板从「typespeed」直接引入，而不是「speed」

这是个容易踩的坑。typespeed 的 `startApp` 会通过调用栈（`getRootPath`）反推应用目录（`MAIN_PATH`），再扫描该目录下的 `.ts` 文件。如果入口从 `speed` 再导出层引入 typespeed，调用栈的"用户帧"会落在 `speed/dist/index.js`，`MAIN_PATH` 被解析到 speed 包内部——扫描时会把 `scaffold/command.d.ts` 当应用文件动态 import，从而误执行 CLI。

所以骨架阶段约定：**`@app` / `ServerFactory` 直接从 `typespeed` 引入**（保证 `MAIN_PATH` 正确落在应用目录）。等 1.3.2 的 `@Service` 落地后，speed 自己的装饰器再从 `speed` 引入。

## 四、怎么扩展：从这里走向注册中心

1.3.0 只做了"门面"。接下来 1.3.1 起，注册中心能力逐 patch 落地：

| patch | 内容 |
|---|---|
| 1.3.1 | 本地注册表 + register/unregister/getInstances 基础 API |
| 1.3.2 | `@Service` 装饰器（声明即注册，注意延迟注册时机） |
| 1.3.3~1.3.4 | 心跳 + 超时摘除 + 优雅注销 |
| 1.3.5~1.3.7 | 服务发现 + 元数据 + 变更监听 |
| 1.3.8~1.3.10 | Nacos 适配 + 持久化 + 高可用 |

**给贡献者的扩展点**：

- 新模板文件：往 `src/scaffold/templates/` 加 `.tpl`，在 `command.ts` 里调 `mkFile`；
- 新模块目录：按 `speed-微服务化开发计划.md` 的约定在 `src/` 下建目录，`package.json` 的 `exports` 加子路径；
- 发布流程：git 操作由 agent 做，`npm publish` 由维护者执行。
