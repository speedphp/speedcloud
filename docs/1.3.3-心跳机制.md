# speed 1.3.3：心跳机制（续租让注册中心知道你「还活着」）

> 版本：speed 1.3.3（依赖 typespeed 2.6.8 的 `ServerFactory.getPort()`）
> 前置：1.3.1 本地注册表、1.3.2 `@Service` 声明/提交两阶段
> 定位：注册中心「正确性」的第一步——健康检查的基础数据源

---

## 一、为什么：注册表只认「注册过」，不认「还活着」

1.3.2 之后，一个服务启动、提交，就进了注册表。但注册表里没有「时间」概念：

```ts
serviceRegistrar.register("user-service", { host: "127.0.0.1", port: 8080 });
// 这条记录从此永远躺在表里——哪怕那个进程已经被 kill 掉
```

这就是 **僵尸实例** 问题：调用方（未来的负载均衡 1.6、RPC 1.8）通过注册表拿实例去调，拿到一个死了的地址，请求直接失败。

业界标准解法是 **心跳续租**：服务注册后，每隔一段时间主动向注册中心报一声「我还活着」，注册中心记录每次心跳的时间戳；超过阈值没报到的实例，才被判定死亡并摘除。

所以心跳机制要回答的问题是：

1. **注册中心怎么知道实例还活着？** —— 靠 `lastHeartbeat` 时间戳持续刷新；
2. **什么时候才敢说它死了？** —— 1.3.4 用「超时阈值」扫描，**本版本不摘除**（心跳失败/停止只留证据，判定摘除是下一个 patch 的事，避免误杀）。

> 关键设计原则（开发计划 1.3.3 技术要点）：**「心跳间隔」与「超时阈值」是两个独立配置项**，且间隔要远小于阈值（业界常见 ≥ 3 倍），否则网络抖动一次就误摘。

## 二、怎么用：注册后启动心跳，一行搞定

`register()` 返回的 `Registration` 句柄新增了 `startHeartbeat()`——注册后调一次，就按固定间隔自动续期：

```ts
import { Service, serviceRegistrar } from "speed";

@Service("user-service")
class UserService {}

public main() {
    this.server.start(8080);
    // 提交注册，拿到句柄
    const registration = serviceRegistrar.register("user-service", {
        host: "127.0.0.1",
        port: this.server.getPort(),   // 真实监听端口（typespeed 2.6.8）
    });

    // 启动定时心跳：默认每 10 秒续期一次
    registration.startHeartbeat();
    // 或自定义间隔（毫秒）：registration.startHeartbeat(5000);
}
```

### 2.1 `Registration` 新增的三个能力

| 方法 | 作用 |
|---|---|
| `renew()` | 手动续期一次：刷新 `lastHeartbeat`。返回 `false` 表示实例已不在注册表 |
| `startHeartbeat(intervalMs?)` | 启动定时心跳（默认 `DEFAULT_HEARTBEAT_INTERVAL_MS` = 10 秒）。**幂等**：重复调用不叠加定时器 |
| `stopHeartbeat()` | 停止定时心跳（优雅停机前调用；`deregister()` 注销成功时也会自动停） |

### 2.2 停机时怎么办

1.3.4 会补「SIGTERM 优雅停机自动注销」；现在可以先手动做：

```ts
process.on("SIGTERM", () => {
    registration.deregister();   // 主动注销：立即移除 + 自动停止心跳
    process.exit(0);
});
```

> `deregister()` 注销成功后会自动 `stopHeartbeat()`，不用担心残留定时器空转。

### 2.3 验收行为（本版本边界）

- 服务周期心跳：注册表里的 `lastHeartbeat` 持续更新 ✓
- 停发心跳：`stopHeartbeat()` 后时间戳**不再前进** ✓（摘除判定留给 1.3.4）
- 心跳失败不立即摘除：实例被注销后 `renew()` 返回 `false`，心跳定时器自动停止，但不会把实例加回来、也不做任何摘除动作 ✓

## 三、原理：`lastHeartbeat` 字段 + 定时续期

### 3.1 数据：`ServiceInstance.lastHeartbeat`

`ServiceInstance` 新增 `lastHeartbeat?: number` 字段：

- `register()` 时自动填充 `Date.now()`（提交即首次心跳）；
- `renew()` 持续刷新它；
- `registeredAt` 只在**注册/重新提交**时刷新，**不再被 `renew()` 覆盖**——注册时间是「何时上线」，心跳是「何时还活着」，两个语义终于分开（1.3.2 占位时 renew 刷 registeredAt 是临时的，本次更正）。

### 3.2 续期：以注册表当前状态为准

`renew()` 的实现不是直接改闭包里的 `target`，而是**回到注册表里按 `serviceName + instanceId` 重新查找**：

```ts
const renew = (): boolean => {
    const current = registry.instances
        .get(serviceName)
        ?.find((item) => `${item.host}:${item.port}` === instanceId);
    if (!current) {
        return false;          // 实例已被注销/摘除：续期失败
    }
    current.lastHeartbeat = Date.now();
    return true;
};
```

为什么要回表查？因为实例可能已经被 `unregister`/`deregister` 掉了，闭包里的 `target` 引用还在，但**表里已经没它了**——直接改 `target` 是「刷一个不存在实例的时间戳」，没有意义。回表查让 `renew()` 的结果反映真实状态。

### 3.3 定时器：幂等 + 失败自停 + 不阻塞退出

`startHeartbeat()` 内部：

```ts
timer = setInterval(() => {
    if (!renew()) {
        stopHeartbeat();       // 目标已不在注册表：停止心跳，避免空转
    }
}, intervalMs ?? DEFAULT_HEARTBEAT_INTERVAL_MS);
timer.unref?.();               // 不阻塞进程退出
```

- **幂等**：已有 timer 时重复调用直接返回，不叠加（叠加会导致同一实例多个心跳定时器，测试里专门验证过）；
- **失败自停**：`renew()` 返回 `false`（实例已不在表）时停止定时器——它已经「死」了，没必要再报心跳；
- **不阻塞退出**：`timer.unref()` 让心跳定时器不阻止 Node 进程自然退出。

### 3.4 边界：本版本为什么不摘除

`renew()` 失败只停自己的心跳，**不做任何摘除**。摘除是「注册中心的判断」：它要扫描所有实例、比较 `now - lastHeartbeat > 超时阈值`，还要处理「阈值设多少不会误杀」（1.3.4 patch 的核心）。心跳只负责「续租」这一件事，职责单一，这是把 1.3.3/1.3.4 拆开的根本原因。

## 四、怎么扩展：从心跳走向健康检查、发现与 Nacos

1. **1.3.4 超时自动摘除**：注册中心加定时扫描，`now - lastHeartbeat > 超时阈值`（默认 ≥ 3 倍心跳间隔，如 30s）判死并摘除；同时补 SIGTERM 优雅停机自动 `deregister()`，把「僵尸实例窗口」压到最小。
2. **1.3.5 服务发现**：`discover(name)` 返回实例时**过滤掉心跳过期的实例**，调用方永远拿不到死地址。
3. **1.3.7 变更监听**：摘除/注销时推送变更事件，订阅方（LB/RPC）本地缓存及时刷新，不用轮询。
4. **1.3.8 Nacos 模式**：Nacos 客户端自带 beat 机制（`NamingService` 自动心跳），`Registration` 接口方法集已对齐（`renew/startHeartbeat/stopHeartbeat` 在 Nacos 实现里委托给 SDK），业务代码无感知切换。
5. **多实例/多副本**：每个实例独立持有一个 `Registration` 句柄、独立心跳——同名多实例各自续租，注册表按 `host:port` 区分，天然支持。
